# Feature Inventory — Total Commander Parity Catalog

Master checklist for feature parity. **Grep by ID (F-xxx), do not load the whole file.**

- **Prio:** P1 = core parity (must), P2 = full parity (should), P3 = optional/macOS extra.
- **Status:** `todo` | `in-progress` | `done` | `n/a-macos` (with rationale) | `post-1.0`.
- Update the Status column the moment a feature is implemented AND tested.
- Source references: TC feature list (ghisler.com/featurel.htm), TC 11 help, plugin
  SDKs (ghisler.github.io).

| F-006 | Drive/volume button bar per panel + drive dropdown combo | macOS: volumes and the drive dropdown are built (ev: symbol:DriveBarView). **Ejecting is not**: this row claimed an eject button and cited `isEjectable` as its evidence, but that property is only read from the filesystem and copied around — no eject or unmount API is called anywhere in the app, the drive bar overrides no `menu(for:)`, and no command exists for it. Reported by a user who has to switch to Finder to eject a stick. The symbol was mistaken for the feature. Picking a plugin drive (TaskManager) switched the panel but left the chip of the last real volume lit — the bar said one thing and the listing another, so the drive read as a mere view switch. The cause is that inside such a mount the panel's path is that mount's own "/", which by longest prefix belongs to the boot drive; the mounted volume now decides the highlight and the path decides only when there is no mount, with no fallback behind it. Carried from the click through `connect`/`fsMount` — which the plugin calls and which was told nothing about the volume the user picked — and remembered per mount frame beside the host fs and return path, so leaving a mount restores the chip that was lit before it instead of guessing. They now take the drive's name from the mount: the tab of the *active* tab only, since switching tabs unwinds to the local filesystem and no other tab can be inside one, and the breadcrumb's leading segment, whose click still goes to "/" — inside a mount that is the drive's own root and nowhere near the local one. What was left was that the drive lived only in the panel: switching tabs or restarting dropped the tab back onto the startup disk's root, since a tab was remembered as its path and that path is the mount's "/". The tab now records the drive it is on (`PanelTabState.driveVolume`, persisted in the session and in a workspace; a record saved before the field existed still loads, since every field after the fourth is optional), and a tab switch or a restore re-enters it — the local path first, then the drive on top, so leaving the restored drive lands in the tab's own directory rather than wherever the panel was standing. Duplicating such a tab duplicates the drive; a *new* tab is a different intent and stays local — anchored to the directory the mount was entered from, since "/" from a mounted drive would open the startup disk's root.
